# تحدي (Tahadi)

منصة للمدربين لتسجيل قياسات العملاء ومتابعة تقدمهم. A platform for fitness coaches to record client measurements and track progress.

| Part | Stack | Hosting |
|---|---|---|
| Database | PostgreSQL | **Supabase** (used only as a database) |
| Backend | Python 3.12 · FastAPI · SQLAlchemy 2 · Alembic · JWT | **Render** (`render.yaml`) |
| Frontend | React 18 · Vite · TypeScript · Tailwind (RTL) · TanStack Query · Recharts | **Vercel** |

### النشر

1. **Supabase**: أنشئ مشروعاً، ثم من *Project Settings → Database → Connection pooling* انسخ:
   - رابط **Transaction pooler** (منفذ `6543`) ← `DATABASE_URL`
   - رابط **Session pooler** (منفذ `5432`) ← `MIGRATIONS_DATABASE_URL`
   - أضف `?sslmode=require` في نهاية كل رابط.
2. **Render**: *New → Blueprint* واختر المستودع؛ سيقرأ `render.yaml`. أدخل قيم `DATABASE_URL` و`MIGRATIONS_DATABASE_URL` و`CORS_ORIGINS`. تُنشأ أسرار JWT تلقائياً، وتُشغَّل الترحيلات قبل كل نشر.
3. **أنشئ حساب المدير** مرة واحدة من *Shell* في Render:
   `SEED_ADMIN_PASSWORD='...' python -m app.db.seed --admin-only`
4. **Vercel**: استورد المستودع، واجعل *Root Directory* = `frontend`، وأضف `VITE_API_URL=https://<اسم-الخدمة>.onrender.com/api/v1`.
5. **الربط**: ضع نطاق Vercel في `CORS_ORIGINS` على Render (مثل `https://tahadi.vercel.app,http://localhost:5173`) ثم أعد النشر.

> الخطة المجانية في Render تتوقف بعد فترة خمول؛ تعرض الواجهة رسالة «جارٍ تشغيل الخادم…» إذا تجاوز الطلب 3 ثوانٍ.

## 🇬🇧 English

### Local development

**With Docker (recommended):**

```bash
docker compose up
```

This starts `postgres:16`, the API (runs `alembic upgrade head`, then `python -m app.db.seed --if-empty`, then uvicorn with reload) and the Vite dev server. Demo logins are in the table above.

**Without Docker:**

```bash
# backend
cd backend
python -m venv .venv && .venv/Scripts/activate      # Windows; use .venv/bin/activate on macOS/Linux
pip install -r requirements.txt
cp .env.example .env                                  # point DATABASE_URL at a Postgres
alembic upgrade head
SEED_ADMIN_PASSWORD=Admin@12345 python -m app.db.seed
uvicorn app.main:app --reload

# frontend
cd frontend
npm install
cp .env.example .env.local
npm run dev
```

**Tests:**

```bash
cd backend && pytest                 # 48 tests: calculations, permissions, flows
cd frontend && npm run build         # type-check + production build
```

By default the backend tests use in-memory SQLite for speed. To run the same suite against Postgres, set `TEST_DATABASE_URL=postgresql://…`. The application itself only runs on PostgreSQL.

### Deploying

#### 1. Supabase (database only)

1. Create a project. In **Project Settings → Database → Connection pooling**, copy:
   - **Transaction pooler** (port `6543`) → `DATABASE_URL`, used by the running app
   - **Session pooler** or direct connection (port `5432`) → `MIGRATIONS_DATABASE_URL`, used by Alembic
   - Append `?sslmode=require` to both. In production the app also enforces SSL if it's missing.
2. Nothing else is needed in Supabase: no Supabase Auth, no client SDK. The React app never talks to Supabase.
3. The first migration runs `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on **every table** (including `alembic_version`) and adds **no policies**. That fully blocks Supabase's auto-generated REST API (anon/authenticated roles get zero rows). The backend connects as the table owner and is unaffected. To verify:
   ```bash
   curl "https://<project>.supabase.co/rest/v1/users?select=*" -H "apikey: <anon key>"   # → []
   ```

Transaction-pooler compatibility: the backend uses psycopg 3 with `prepare_threshold=None` (no server-side prepared statements) and `NullPool` in production.

#### 2. Render (backend)

1. **New → Blueprint**, then pick the repo. Render reads `render.yaml` (`rootDir: backend`, `preDeployCommand: alembic upgrade head`, health check `/api/v1/health`).
2. Fill in the `sync: false` variables: `DATABASE_URL`, `MIGRATIONS_DATABASE_URL`, `CORS_ORIGINS`. `JWT_SECRET` and `JWT_REFRESH_SECRET` are generated by Render.
3. Create the first admin **once** from the Render Shell:
   ```bash
   SEED_ADMIN_PASSWORD='a-strong-password' python -m app.db.seed --admin-only
   ```
   (Leave out `--admin-only` and set `SEED_DEMO_PASSWORD` if you want the demo trainers and clients.) The seed refuses to run when any user exists, so it can't run twice.
4. Check `https://<service>.onrender.com/api/v1/health`, which should return `{"status":"ok","database":"ok"}`.

#### 3. Vercel (frontend)

1. Import the repo. Set **Root Directory** = `frontend`, Framework = Vite, Build = `npm run build`, Output = `dist`.
2. Environment variable: `VITE_API_URL=https://<service>.onrender.com/api/v1`.
3. `frontend/vercel.json` rewrites every path to `index.html`, so deep links like `/trainer/clients/3` survive a refresh.

#### 4. Connect the two

- On Render, set `CORS_ORIGINS` to a comma-separated list, e.g. `https://tahadi.vercel.app,http://localhost:5173`, then redeploy.
- `CORS_ORIGIN_REGEX` (default `https://tahadi-.*\.vercel\.app`) also allows Vercel preview URLs. Every other origin is rejected.

### Environment variables

| Variable | Where | Purpose |
|---|---|---|
| `ENVIRONMENT` | backend | `production` enables SSL enforcement, NullPool, and a refusal to start with default secrets |
| `DATABASE_URL` | backend | Supabase transaction pooler (6543) |
| `MIGRATIONS_DATABASE_URL` | backend | Supabase session pooler / direct (5432) |
| `JWT_SECRET`, `JWT_REFRESH_SECRET` | backend | separate secrets for access and refresh tokens |
| `ACCESS_TOKEN_MINUTES`, `REFRESH_TOKEN_DAYS` | backend | token lifetimes (30 min / 14 days) |
| `CORS_ORIGINS`, `CORS_ORIGIN_REGEX` | backend | allowed frontend origins |
| `LOGIN_RATE_LIMIT`, `LOGIN_RATE_WINDOW_SECONDS` | backend | login throttling per IP (10 per 60 s) |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `SEED_DEMO_PASSWORD` | backend | one-time seed |
| `VITE_API_URL` | frontend | backend base URL including `/api/v1` |

### Design decisions

**Tokens across domains.** The frontend (`vercel.app`) and API (`onrender.com`) are on different sites, so auth uses the `Authorization: Bearer` header, not cookies:
- The **access token** (30 min) lives **in memory only**.
- The **refresh token** (14 days) is kept **in memory + `localStorage`** so a page reload can silently restore the session (`POST /auth/refresh`, which rotates both tokens).
- An Axios interceptor refreshes once on a 401 (single-flight, so parallel requests share one refresh) and retries the request; if the refresh fails, the user is logged out.
- Trade-off: `localStorage` is readable by injected JavaScript. If you put both apps on one custom domain (e.g. `app.tahadi.com` + `api.tahadi.com`), switch the refresh token to an `httpOnly; Secure; SameSite=None` cookie.

**Authorization lives on the server.** `require_role(...)` and `get_accessible_client(...)` (in `app/core/deps.py` and `app/services/permissions.py`) are the single source of truth:
- A trainer asking for another trainer's client gets **404** (existence is never leaked). The same goes for a client asking for another client.
- Any POST/PUT/DELETE on measurements by a client gets **403**, because the role check runs before the lookup.
- The client's `PATCH /auth/me` schema forbids extra fields, so role, trainer, height, sex, and birth date can't be changed (**422**).

**Other choices:**
- **Calculations** (`app/services/calculations.py`) are pure functions. Age is computed at the **session date**. BMI, WHR, BMR, and TDEE are computed on the fly, never stored.
- **Weight direction depends on the goal:** fat_loss means down is good, muscle_gain means up is good, and for fitness/health it's by BMI (≥25 down, <18.5 up). This drives the green/red/grey chips.
- **Measurement ranges** are stored on each definition (`min_value`/`max_value`, editable by the admin) and validated on both client and server, with Arabic messages.
- **Audit log:** every session create/update/delete writes `audit_log` with a before/after snapshot. User deletion is a **soft delete**, and measurement deletion is a hard delete that's audited.
- **Calculator page:** it computes instantly in the browser using formulas that mirror the backend, so it works even while a sleeping server wakes up. `POST /calculate/bmr-tdee` is also available.
- **Charts are RTL:** the earliest date is on the right and the Y axis is on the right. Digits are Western (0-9) and dates are Gregorian with Arabic month names.
